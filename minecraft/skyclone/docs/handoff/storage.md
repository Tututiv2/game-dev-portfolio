# storage — hand-off

Package `com.skyclone.mod.storage` (entry `StorageModule`), data `resources/data/storage/` (generated by
`tools/gen/storage/gen_storage.py` from `research/data`), renames `docs/names/storage.md`, unit tests
`plugin/src/test/java/com/skyclone/mod/storage/StorageMathTest.java`.

Provides **`Features.Storage`** (`openStorage`, `openWardrobe`; wave 5 public extras `openEquipmentWardrobe`, `wardrobeItems`,
`equipmentWardrobeItems`) and **`Features.Sacks`** (`count/remove/add/openMenu`). Registers core's dupe-scan source `storage`.
Note: the `Features.Sacks` javadoc says "Provided by sacks" — there is no sacks module; storage provides it (brief).

## What works (verified how)
Verified by `bash tools/check.sh storage` (CHECK OK, 190 files as of wave 3), 12 JUnit tests (all pass: run by hand with the
JUnit launcher against the real generated JSON), and 9 self-tests written for the integrator's live run. **Not yet
driven by a real client** (no dev server for module agents).

## What is partial / not built
- **Nothing in waves 3-5 has been driven by a client** (compile + JUnit + self-tests written). Highest-value live checks:
  shift-click a chestplate/leggings/boots into the Wardrobe (own row), the slot button flipping Empty -> Ready,
  `/gfs wheat 64`, `/sacks mining`, Settings > Sacks Messages off; wave 5: `/eqwardrobe` shift-click a cloak (lands in
  row 2), Take Set; `/sacks rune` grouped view; Storage > right-click a backpack > Apply Skin; `/sb storage dupesrc <p>`.
- **Equipment Wardrobe cannot put a set ON yet.** Accessories owns the worn slots and `Features.Equipment` is provided
  as a lambda with only `worn(p)`. Until accessories adds `equipped(p, slot)` + `setEquipped(p, slot, item)` (request
  9), the slot button is **Take Set** (moves the set into the inventory, all or nothing) and the player right-clicks
  each piece on. The swap code, Link Equipment and the admin `equip/unequip` are written and turn on by themselves
  the moment the provider has those two methods (`/sb storage info` says `bridge live`).
- **Backpack skins have no source** but admin give: the reference sells them in Fire Sales / event shops (extras
  request 10). On a skinned backpack carried in the inventory the head texture depends on extras' look pass (we set
  its `skyclone:extras_skin` key); inside `/storage` we draw it ourselves.
- **Unregistered sack contents**: the 24 trophy frogs are now registered by **galatea** (its Professor also sells the
  Bronze/Silver frog sacks), so `/sb storage missing` should be ~1 (one Witch item) - not re-measured live.
- `EXTRA_LARGE_GEMSTONE_SACK` capacity (12,800,000) and Gold/Diamond trophy sack capacities (512) are TUNE (no lore
  data in research, re-checked wave 5). Gold/Diamond **trophy fishing** sacks still have no source (fishing awards
  Bronze/Silver; NEU has no card for them either). Sack of Sacks unlock size (3) and the vault table are TUNE.
- **Eerie pet "Shared Dread"** (Fear from spook armour in the wardrobe counts unworn) is armor's to apply; the reader
  exists here (`wardrobeItems(p)`, request 11).
- Vanilla `/give` arrows/items that never got converted still store under their vanilla id (core alias) - correct
  but untested live.

## Known risks
1. **Untested live UI.** The free-slot sync relies on core's next-tick `onFreeSlotChange` + `onClose` + my
   `ProfileUnload` flush; a client edge case (drag across many slots, number-key swaps, quitting mid-click) could still
   lose or duplicate an item. The uuid guard deletes duplicate uniques, but stackables have no uuid — a stackable dupe
   through a storage menu would not be caught. Please exercise with a real client.
2. **Sacks swallow loot by default.** Anything a sack accepts goes into it (as in the genre). Modules that check the
   INVENTORY for an item right after giving it (quests, "hand in 10 wheat") must also look at `Features.Sacks.count`.
3. **Profile data size.** A full player can hold ~1,200 serialized stacks; they are split over 5 member keys so a sack
   change does not re-serialise the ender chest, but each key is re-serialised by core's 10 s autosave check.
