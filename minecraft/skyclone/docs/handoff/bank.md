# bank — hand-off

Package `com.skyclone.mod.bank` (entry `BankModule`). Owns: the bank (co-op + personal accounts, seven
account tiers, seasonal interest, history, the Pocket Bank), the **Boon Cookie** (our booster cookie) and its
**Boon Buff** with bits and fame, the **Community Shop** (cookie, Bits Shop, fame ranks, timed account/profile
upgrades) and the secure player-to-player **`/trade`**. Provides no `Features` interface (none exists for it);
other modules reach it through commands and requirement keys (below).

Data: `plugin/src/main/resources/data/bank/*.json`, all generated by `python tools/gen/bank/gen_bank.py` from
research 05 (tables 1.2, 1.3, 6.3, 6.4), research 02 (bank-upgrade SkyBlock XP) and the NEU repo (Bits Shop =
`ELIZABETH_NPC` shop recipes, Pocket Bank recipe + skull, NPC skins). The generator cross-checks itself: every
interest band's "coins from full band" = width x rate, and each tier's summed bands = its "Max interest / season".
Re-run it, never hand-edit the JSON. Renames: `docs/names/bank.md`.

## Contract for other modules

- **Requirement keys** this module resolves: `cookie` (Boon Buff active) · `cshop:<upgrade>:<tier>` (Community Shop
  upgrade owned; ids: `island_size, minion_slots, guests_limit, coop_slots, coins_allowance, armor_wardrobe,
  equipment_wardrobe, loadout_slots, hotm_slots, ender_chest_pages, accessory_bag, sack_of_sacks, magic_find,
  bazaar_flipper, garden_farming_fortune`; values per tier in `data/bank/upgrades.json`) · `fame:<n>` · `famerank:<index>`.
- **Do NOT read this module's profile keys (`bank`, `bank_account`) with a mirror class.** Core's `ProfileService.resolve`
  converts the live object into the asking class and KEEPS the converted one, so every field the mirror lacks is lost
  (cookie, bits, fame...). Use the requirement keys above (`cookie`, `fame:<n>`, `famerank:<i>`, `cshop:<id>:<tier>`).
- **`Features.Bank`** (wave 5): `openMenu`, `cookieActive`, `cookieMillisLeft`, `bitsMultiplier`. Bits you award get the
  fame multiplier automatically (reason must start with your module id, e.g. `slayer: ...`); calling `bitsMultiplier`
  marks you as applying it yourself.
- Reading `cshop:<id>:<tier>` makes that upgrade buildable (auto-live); no dial edit needed.
- Stat providers: `bank.cookie`, `bank.upgrades`. Tab widgets: `bank.account` (140), `bank.cookie` (145).
- Objective completed: `deposit_coins` (first deposit). Talking to a banker is detected by progression from the NPC anchor.
- SkyBlock XP keys: `bank:<tier id>`, `community:<upgrade>:<tier>`.

## Known risks

1. **Trade is the riskiest code and has no live run.** Escrow ordering (remove from inventory → save player data → file
   row) and delivery ordering (delete row → give) were chosen so a crash can lose an item in flight but never duplicate one;
   `Player.saveData()` is called on every offer/return. Two real clients should exercise offer/take-back/coins/accept,
   quit mid-trade, distance cancel, and a restart with items in escrow (they come back at next login).
2. **Tier gates may feel unreachable**: Gold 100K Gold collection and museum milestones come straight from the research; if the
   collections/progression numbers differ, relax with `bank.upgrade.gold-scale` / `bank.upgrade.museum-per-milestone` (0 disables).
3. **Interest is paid lazily** (when a member of the profile is online), compounding missed payouts up to 12; a profile nobody
   opens for months is paid at most 12 payouts on return (`bank.interest-max-catchup`). Co-op members online together share one
   shared-data object, so a payout cannot double; the period is saved before the coins move.
4. **Account-wide state (Wave 3) has no live run.** A crash can lose up to 20 s of buff/bits/fame changes made since
   the last snapshot only if the player then plays ANOTHER profile first (the profile's own copy is newer and gets
   published otherwise). The first switch after deploying Wave 3 merges each legacy profile copy once (see Wave 3 #3).

## Playtest fixes (2026-10-03)

- **Rounding (playtest-newplayer, minor): "Withdraw half of 102.5" showed "Withdrew 51.2" / "51.3 remain",
  and half of a 407.5 purse showed 203.7.** Root cause: the fraction buttons computed `balance / 2` and
  `balance * 0.2` in doubles, giving amounts the economy cannot hold (51.25, 203.75; core stores TENTHS),
  which `floorTenth` then truncated silently between the button and the chat line. Now every fraction is
  computed in tenths by `BankMath.share(tenths, num, den)` (rounded DOWN, the odd tenth stays where it was;
  `BankMath.tenthsOf` reads a purse/bank double back to its exact tenths), and the icon and the click call
  the SAME helper (`BankMenus.depositTenths` / `withdrawTenths`, capped by room in tenths). Each amount icon
  now shows the amount AND what is left ("Left in the account: 51.3" / "Purse after: 203.8"), so the
  uneven split is visible before the click and matches the chat message exactly. A typed amount finer
  than a tenth (51.25) gets a grey note "Coins move in tenths: 51.25 was rounded down to 51.2"
  (`Accounts.roundedNote`; only when the typed amount, not purse/room/balance, decided the move).
  `BankMath.commas` still rounds DOWN (projections such as interest are credited rounded down by core);
  moved amounts are whole tenths before they reach it. Unit test `sharesAreWholeTenthsAndAddUp`.
  Verified: `tools/check.sh bank` CHECK OK, BankMathTest 9/9. Not re-checked in a real client.
