# SKYCLONE — THE BUILD CONTRACT

> Every agent reads this whole file before writing a line. It is the only thing that lets ~30
> agents build one game at the same time without breaking each other. When this file and your
> instincts disagree, this file wins. When this file is silent, read the API javadoc in
> `plugin/src/main/java/com/skyclone/api/` — it is part of the contract.

## 0. What we are building

A **complete SkyBlock-genre MMO** as a Paper plugin (Minecraft 26.1.2, Java 25), modelled
system-for-system on Hypixel SkyBlock: islands, skills, collections, minions, crafting with
enchanted materials, reforges, enchants, pets, accessories, slayers, mining with Heart of the
Mountain, farming + the Garden, fishing with sea creatures, the Bazaar, the Auction House, banks,
mayors, the calendar and its festivals, and (last) dungeons. The owner wants to log in and play a
FULL game — every menu clickable, every number real.

**Owner's answers (2026-10-02):** Paper plugin · built for a PUBLIC server eventually (so: anti-dupe,
transactional economy, nothing trusts the client) · EVERY world is generated by code, nothing is
hand-built · deepest first pass on **Slayers, Mining (HOTM/Crystal Hollows), Garden/farming/fishing**,
dungeons last.

Working title **SkyClone**. The display name of the server is a dial and will change; never bake
"SkyClone" into lore or dialogue.

### The research (read the parts for your system — the numbers are there)
`research/01..08-*.md` (per-system reference, 1,300–3,100 lines each) and `research/09-api-data.md`,
which describes the raw data in `research/data/`:
- `items.json` — all 5,655 reference-game items: id, material, tier, category, stats.
- `skills.json`, `collections.json` — exact XP curves and collection tiers.
- `neu-repo/items/*.json` — per-item JSON with **recipes**, NPC shop prices, mob drop tables,
  lore and skull textures. `neu-repo/constants/*.json` — enchants, reforges, pets, slayer XP,
  dungeon XP, HOTM, gems, garden, minions.
- `skyhanni-repo/` — sea creatures, minion drops, accessory data.
Generate your data files FROM these with a script (keep the script in `tools/gen/<module>/`)
rather than typing tables by hand. Never ship real player UUIDs from the auctions sample.

## 1. Hard rules

1. **Rename proper nouns.** Mechanics and numbers are not copyrightable; names, text and art are.
   Every invented proper noun of the reference game (item names like "Aspect of the End",
   "Hyperion"; boss names like "Revenant Horror"; NPC names like "Maddox", "Elizabeth"; unique
   place names) gets OUR OWN name in the same spirit. Generic words stay generic
   ("Enchanted Diamond", "Zombie", "Bazaar", "Auction House", "Hub", "Diamond Sword", "Spider's
   Den" is generic enough to keep). Internal IDS keep the reference game's id (`ASPECT_OF_THE_END`)
   so that every module means the same thing by the same id — ids are never shown to players.
   Write every rename you make to `docs/names/<module>.md` as a table
   `| id | reference name | our name |` so the owner can review them in one place.
   Never copy the reference game's lore text verbatim — rewrite descriptions in your own words
   (keep the numbers).
2. **No pay-to-win, no real money, no gambling minigames.** There are no gems/ranks for sale.
   Bits are EARNED in game (from the booster-cookie equivalent bought with coins, and from
   contests/events). Anything the reference game gates behind a paid rank is gated by SkyBlock
   level or simply free.
3. **Every tunable is a dial** (`Sky.dials()`), editable in game with `/sb dial set`. Nobody edits
   YAML. Every admin action has an `/sb <sub>` command. Every player feature has a command AND a
   menu path.
4. **Public-server safe.** Menus cancel every click outside declared free slots. Unique items carry
   a uuid. Anything that moves coins or items between players (trade, auction, bazaar, co-op) is
   a DB transaction with the item escrowed before the coins move. Validate every input server-side.
   Rate-limit anything a player can spam. Never `dispatchCommand` with player text.
5. **Stay in your lane.** You own exactly the files listed in your brief (normally
   `plugin/src/main/java/com/skyclone/mod/<id>/**`, `plugin/src/main/resources/data/<id>/**`,
   `tools/gen/<id>/**`, `docs/names/<id>.md`, `docs/handoff/<id>.md`). You do NOT edit `api/`,
   `core/`, `SkyPlugin.java`, `plugin.yml`, `build.gradle.kts`, `ModuleList.java`, or any other
   module. If you need something from them, write it under "Requests" in your handoff file and
   work around it (no-op, fallback) — the integrator will wire it.
6. **No cross-module imports.** `com.skyclone.mod.a` never imports `com.skyclone.mod.b`. Talk
   through `Sky.*`, `Sky.service(Features.X.class)`, the events in `SkyEvents`, item/mob/recipe
   ids, island anchors, and requirement keys. `tools/check.sh <id>` compiles your module against
   api+core ONLY, so a cross import fails your check.
7. **Main thread for Bukkit, DB thread for SQL.** Never block the main thread on I/O.
   `Sky.db()` futures complete off-thread; hop back with `Bukkit.getScheduler().runTask`.
8. **Your scratch space is yours.** Temporary files go in
   `%TEMP%\skyclone\<your-module-id>\` (Bash: `$TMPDIR/skyclone/<id>/`). Never use a shared
   filename in a shared folder — research agents overwrote each other doing exactly that.
9. **No control characters in source.** Write Java with the file-writing tool, not through shell
   heredocs or non-raw Python strings (a `\b` became a literal backspace in this portfolio four
   times). `check.sh` fails on them.
10. **Don't start the dev server.** There is one, and the integrator owns it. You verify with
    `check.sh`, your unit tests, `tools/preview.sh` (builders), and self-tests that the integrator
    runs live.

## 2. Architecture in one screen

```
com.skyclone.SkyPlugin            boots core, then every module in core.ModuleList order
com.skyclone.api.*                THE CONTRACT. Interfaces + data classes. Read the javadoc.
   Sky                            static door to every service
   GameModule                     enable() / postEnable() / disable()
   stat, item, ability, combat, mob, loot, player, economy, profile, data,
   config, command, time, util, ui, npc, world, world.gen, event, skill, feature
com.skyclone.core.*               implementations of the core services (phase B)
com.skyclone.gen.*                PURE builder toolkit: shapes, noise, trees, palettes,
                                  MemoryCanvas, Walkability, PreviewRenderer (no Bukkit)
com.skyclone.mod.<id>.*           one feature module per id (phase C)
resources/data/<id>/*.json        that module's data
```

**Core services** (always there): `Sky.db()`, `profiles()`, `economy()`, `items()`, `recipes()`,
`stats()`, `vitals()`, `combat()`, `abilities()`, `mobs()`, `loot()`, `worlds()`, `npcs()`,
`menus()`, `sidebar()`, `commands()`, `dials()`, `calendar()`, `requirements()`.

**Feature services** (owned by a module, never null): `Sky.service(SkillService.class)` and every
interface nested in `api.feature.Features` — Collections, Sacks, Pets, Accessories, Mayors,
SkyLevel, PrivateIsland, Objectives, Bazaar, Auctions, Storage, Slayers, Dungeons, Mining, Garden,
Bestiary, Museum, Equipment, Potions, SkyMenu, Essence, Party, and (wave 5) Settings, Soulflow, Hunting,
Abiphone, Bank, Rift — see `docs/handoff/core-wave5.md`. If you OWN one, `Sky.provide(X.class, impl)` in
`enable()`. If you USE one, call it at use time (it may be a no-op proxy returning 0/false/null —
handle null).

### Boot order
1. core (db → profiles → economy → dials → commands → requirements → calendar → items → recipes →
   stats → vitals → abilities → combat → mobs → loot → worlds → npcs → menus → sidebar)
2. every module's `enable()` in ModuleList order
3. every module's `postEnable()`
4. islands whose generator version changed are (re)built, NPCs spawn, spawners start
5. commands are registered with Paper

### A module's skeleton
```java
package com.skyclone.mod.slayer;

public final class SlayerModule implements GameModule {
    @Override public String id() { return "slayer"; }

    @Override public void enable() {
        Sky.items().loadJson("slayer", "items.json");
        Sky.mobs().loadJson("slayer", "mobs.json");
        Sky.recipes().loadJson("slayer", "recipes.json");
        Sky.provide(Features.Slayers.class, new SlayerServiceImpl());
        Sky.requirements().register("slayer", new SlayerRequirement());
        Bukkit.getPluginManager().registerEvents(new SlayerListener(), Sky.plugin());
        Sky.commands().register(SkyCommand.of("slayer", "Open the slayer menu").playerOnly().run(...));
        Sky.commands().admin("slayer", "<player> <type> <xp>", "Give slayer XP", ...);
        Sky.commands().selfTest("slayer.drops-exist", () -> ...);
        Sky.sidebar().section("slayer", 200, p -> questLines(p));
    }
}
```

## 3. Conventions

### IDs
- Items: UPPER_SNAKE, the reference game's id when one exists (`research/data/items.json`).
- Mobs: lower_snake, unique across the game, prefixed by island when generic
  (`hub_graveyard_zombie`, `end_zealot`).
- Enchants, reforges, abilities, set ids, NPC ids, dial keys, self-test ids: lower_snake,
  prefixed with your module when not obviously unique.
- Islands (exact): `hub, private_island, barn, mushroom_desert, park, gold_mine, deep_caverns,
  dwarven_mines, crystal_hollows, glacite_tunnels, spiders_den, the_end, crimson_isle,
  jerrys_workshop, dungeon_hub, catacombs, garden, rift, backwater_bayou, kuudra`.

### Item ownership (who REGISTERS which ids — everyone else only references them)
| Owner | Items |
|---|---|
| materials | generic materials + every ENCHANTED_* compression item and their compression recipes, vanilla-derived resources. Registers in **postEnable and only if absent**, so any specialist module's definition wins. |
| armor | every armor set EXCEPT slayer, dungeon, crimson/kuudra and fishing-rod-adjacent sets owned below; includes skill armors (farm suit, mushroom, miner's, glacite, fishing armors) |
| weapons | every sword/bow/wand/longsword EXCEPT slayer and dungeon drops; arrows; quivers' arrow types |
| mining | pickaxes, drills + parts + fuel, gemstones (rough→perfect), powders' items, HOTM items, forge outputs that are mining gear, ores' mining-only drops (mithril, titanium, glacite...) |
| farming | hoes, farming tools, crop-specific items not covered by materials, contest medals/items |
| garden | garden-only items (compost, copper shop items, pest drops, vacuums, sprays) |
| foraging | axes (incl. treecapitator), foraging-only drops |
| fishing | rods + rod parts, baits, sea creature drops, trophy fish items |
| slayer | slayer drops, slayer weapons/armor/accessories crafted from slayer drops? — NO: accessories stay with accessories; slayer owns drops, slayer weapons, slayer armor |
| combatzones | Spider's Den / The End mob drops, dragon drops & dragon armor... (dragon ARMOR sets belong to armor; dragon fragments belong here) |
| crimson | Crimson Isle drops, crimson armors, faction items |
| accessories | every talisman/ring/artifact/relic, power stones, equipment-slot items (necklace/cloak/belt/gloves) |
| pets | pets, pet items, pet candy, Kat materials |
| minions | minion items (all types × tiers), minion upgrades, fuels, storage chests |
| enchanting | enchanted books, experimentation rewards |
| reforges | reforge stones, recombobulator, hot/fuming potato books, essence (if not dungeons) |
| alchemy | potions, alchemy-only ingredients |
| storage | backpacks, sacks, the ender-chest items |
| bank / bazaar / auction / shops / menus / mayors / progression | only their own special items (booster cookie equivalent, cake, fairy soul tokens...) |
| dungeons (wave 2) | dungeon items, essences, dungeon armor/weapons |

Duplicate registration: core keeps the FIRST registration and logs the second. That is why
materials goes last. If you need an item you don't own, reference its id; if the owner might not
make it, add it to your handoff "Requests" — do NOT register it yourself.

### Text
- '&' legacy codes everywhere (`Text.c("&6Gold")`). Italic is always off.
- Rarity colours via `Rarity.code()`. Stat labels via `Stat.label()` ("&c❁ Strength").
- Body text `&7`, positive `&a`, warnings `&c`, click hints `&eClick to ...!`, numbers coloured.
- Numbers: `Text.commas`, `Text.shortNum`, `Text.roman` for tiers/levels, `Text.duration`.
- Chat formats via `Msg` (level-up boxes, `[NPC] Name: line`, RARE DROP!).

### Menus (`api.ui.Menu`)
- Default 6 rows. `chrome()` = black glass + Close at 49; `back(where, supplier)` = Go Back at 48.
- Icons: `Icons.of(...)`, `Icons.skull(texture, ...)`. Last lore line of a clickable icon is
  `&eClick to <verb>!`. Locked things show `&cLocked` and say what unlocks them
  (`Sky.requirements().describe(key)`).
- Every menu reachable from a command AND from the SkyBlock Menu (nether star) tree where the
  reference game has it there. The **menus** module owns the SkyBlock Menu and calls your
  `openMenu` through your Features interface — make sure you provide it.
- Paged lists: `Sky.menus().paged(...)`. Confirmations: `Sky.menus().confirm(...)`. Text input:
  `Sky.menus().input(...)`.

### Persistence
- Per-player: `Sky.profiles().member(p, "<module>", MyData.class)` — plain class, public no-arg
  constructor, Gson-friendly fields (maps, lists, primitives, strings; no Bukkit objects). Mutate
  in place; core saves. Use `shared(...)` for co-op-shared state. Initialise per-player things on
  `SkyEvents.ProfileReady`, never on PlayerJoinEvent.
- Global: `Sky.db().migrate("<module>", 1, "CREATE TABLE <module>_x (...)")` in enable, then
  `Sky.db().transaction(...)`.

### Data files
`plugin/src/main/resources/data/<module>/items.json | mobs.json | recipes.json | spawns.json |
...` — arrays of the API data classes (ItemDef, MobDef, Recipe, SpawnRule). Load with
`Sky.items().loadJson("<module>", "items.json")` etc. Your own extra files: read with
`Sky.plugin().getResource("data/<module>/x.json")` + Gson. Keep files under ~2 MB each; split by
category if bigger.

### Commands
- Player commands mirror the reference game where they exist (`/bz`, `/ah`, `/pets`, `/wardrobe`,
  `/storage`, `/sacks`, `/collection`, `/skills`, `/craft`, `/recipe <item>`, `/warp <dest>`,
  `/hub`, `/is`, `/slayer`, `/hotm`, `/garden`, `/calendar`, `/bank`, `/trade <player>`,
  `/coop`, `/visit <player>`, `/sbmenu`, `/pv [player]`, `/equipment`, `/accessories`,
  `/potionbag`, `/quiver`, `/fishing`, `/bestiary`, `/museum`, `/election`).
- Admin: `/sb <sub>` via `Sky.commands().admin(...)`. Give each admin action to test your system
  quickly (`/sb slayer spawn zombie 4`, `/sb mining powder add mithril 10000`).
- Descriptions are mandatory — `/commands` lists everything from the registry automatically.

### Requirement keys (`Sky.requirements()`)
`skill:<skill>:<lvl>`, `collection:<ITEM_ID>:<tier>`, `slayer:<type>:<lvl>`, `catacombs:<lvl>`,
`class:<class>:<lvl>`, `hotm:<lvl>`, `hotf:<lvl>`, `sblevel:<lvl>`, `garden:<lvl>`,
`bestiary:<family>:<tier>`, `quest:<id>`, `visited:<island>`, `faction:<name>:<rep>`,
`mp:<magical power>`. Whoever owns the system registers the resolver for its prefix.

### Self-tests (required, at least 3 per module)
`Sky.commands().selfTest("<module>.<what>", () -> null-or-error)`. Must check your DATA hangs
together: every item id you reference exists (`Sky.items().exists`), every mob drop exists,
every recipe ingredient exists, every anchor you need exists in the built layout, your menus build
without throwing, a formula returns the research doc's number for a known input.

## 4. The world: islands, anchors, areas, zones

Every island is generated by a PURE `IslandGenerator` (no Bukkit imports) writing into a
`VoxelCanvas` and describing itself in a `Layout`: **anchors** (named points), **areas** (named
boxes) and **zones** (named boxes players are "in", shown on the sidebar as `⏣ Name`, smaller wins).
Builders see their work with `bash tools/preview.sh <GeneratorClass>` → top-down and isometric
PNGs (read them with the Read tool — LOOK at them) plus a walkability report.

**Builder rules** (paid for in this portfolio's other servers):
- Players arrive at `spawn` and must be able to WALK to every NPC anchor, portal and named area
  that is meant to be walked to. `preview.sh` floods from `spawn` and lists every anchor it cannot
  reach. Zero unreachable anchors before you hand off.
- Nothing may float, no stairs to nowhere, no roof gaps, no buildings overlapping (reserve a box
  per building first, then build inside it).
- Additive passes before carving passes.
- Make it look like a PLACE: varied palettes, paths, lighting (lanterns/lamps every ~12 blocks in
  towns), trees, fences, decoration, landmarks visible from spawn. Not boxes on a plane.
- Scale: the hub is roughly 600×600 with distinct districts; other islands 150–500 across.
- Portals: an area named `portal.<warpId>` (2–4 wide, framed visibly) — core teleports anyone who
  walks into it to that warp. Each island also has a portal back to the hub.

## 5. Combat, stats, items — how the pieces meet

- Stats: register a `StatProvider` for anything that grants stats (skills, pets, accessories,
  potions, set bonuses, mayors, HOTM perks). Item-instance stats (enchants that add Defense,
  gems, stars) are an `ItemStatContributor` so the lore matches the player's real stats.
- Damage: a `CombatService.DamageModifier` for anything that changes damage (Sharpness, slayer
  bonus vs. type, pet abilities, armor sets). Priorities: 100 enchants, 200 sets, 300 pets,
  400 slayer/dungeon/mayor, 900 final.
- Abilities: put an `AbilityDef` on the ItemDef; implement it with
  `Sky.abilities().register("<ability_id>", use -> {...; return true;})`.
- Mobs: `MobDef` (data) + optional `MobBehaviour` (code) + `SpawnRule` (where). Kill → MobKill event →
  loot via `Sky.loot()`. Skills grants combat XP from the event. Bestiary, slayer progress,
  collections all listen to events — never call them directly.
- Items that a player EARNS go through `Sky.loot().give(...)` so collections and sacks see them.

## 7. Definition of done for a module

1. `bash tools/check.sh <id>` prints `CHECK OK`.
2. Breadth: the system is complete at the reference game's breadth — all tiers, all variants,
   all menus — not a sample. If you could not finish, say exactly what is missing in the hand-off.
3. ≥3 self-tests, renames file, hand-off file.
4. Every number traces to the research or is marked `// TUNE:` with why.
5. Every player-facing feature reachable by command and by menu; every tunable a dial.
